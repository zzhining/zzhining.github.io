"어떤 업무부터 자동화하면 될까요?"

1. 기업 AI 교육 현장에서 가장 많이 받는 질문이다. 도구를 배우기 전에 이 질문에 먼저 답해야 한다. 자동화가 가능한 업무인지, 어떤 구조로 설계해야 하는지를 판단하는 사고법이 없으면 도구를 배워도 적용이 되지 않는다.

2. 4편에서는 워크플로우 설계의 핵심 사고법을 다룬다. 업무를 분해하는 방법, 노드를 연결하는 원리, 조건 분기와 반복 처리를 언제 쓰는지를 순서대로 정리한다. Dify는 이 흐름을 캔버스로 시각화하는 도구로 활용한다.

---

## 1. 워크플로우 설계의 출발점: 업무 분해

3. 워크플로우 설계는 자동화하려는 업무를 세 층위로 분해하는 것에서 시작한다.

```
Input   → 무엇이 들어오는가
Process → 무엇을 처리하는가 (단계별로)
Output  → 무엇이 나가는가
```

4. 대부분의 업무는 이 세 층위로 쪼갤 수 있다. 예를 들어 "주간 보고서 작성"이라는 업무를 분해하면 이렇다.

```
Input   : 이번 주 업무 내용 (텍스트 또는 파일)
Process : 1. 핵심 내용 추출
          2. 성과와 이슈 분류
          3. 다음 주 계획 도출
          4. 보고서 양식에 맞게 작성
Output  : 완성된 주간 보고서
```

<!-- [이미지: Input → Process → Output 분해 다이어그램.
왼쪽에 "주간 보고서 작성" 박스,
오른쪽에 세 층위로 분해된 구조 표시.
Process 안에 4단계가 순서대로 나열된 형태] -->

5. 이 분해가 명확할수록 워크플로우 설계가 쉬워진다. Process의 각 단계가 곧 워크플로우의 노드가 된다. 분해가 모호하면 노드를 어디서 끊어야 할지 판단이 서지 않는다.

---

## 2. 노드: 워크플로우의 최소 단위

6. 워크플로우는 노드(Node)를 연결해서 만든다. 노드는 하나의 처리 단계다. 레고 블록처럼 각 노드를 연결하면 하나의 자동화 파이프라인이 완성된다.

Dify 기준으로 자주 쓰는 노드는 다섯 가지다.

| 노드 | 역할 | 언제 쓰는가 |
|---|---|---|
| 시작(Start) | 입력을 받는다 | 모든 워크플로우의 첫 노드 |
| LLM | AI가 텍스트를 처리한다 | 요약, 분류, 생성, 번역 등 |
| 조건 분기(IF/ELSE) | 조건에 따라 흐름을 나눈다 | 카테고리별 처리가 달라질 때 |
| 반복(Iteration) | 같은 처리를 여러 번 한다 | 리스트 항목을 하나씩 처리할 때 |
| 출력(End) | 최종 결과를 내보낸다 | 모든 워크플로우의 마지막 노드 |

<!-- [이미지: Dify 캔버스 기본 노드 배치 다이어그램.
"시작 노드 → LLM 노드 → 출력 노드" 순서로 연결된 가장 단순한 구조.
각 노드를 사각형 박스로 표시하고 화살표로 연결.
노드 내부에 역할 텍스트 표시] -->

---

## 3. 시작 노드: 입력을 설계한다

7. 시작 노드는 사용자로부터 무엇을 받을지 정의하는 곳이다. 여기서 설정한 변수가 이후 모든 노드에서 참조된다.

입력 필드 유형은 크게 네 가지다.

```
짧은 텍스트 : 이름, 제목, 키워드 (최대 256자)
문단        : 긴 본문, 이메일 초안 등
선택        : 드롭다운 옵션 (예: 톤 선택 - 격식체 / 친근한)
파일        : PDF, CSV 등 파일 업로드
```

<!-- [이미지: 시작 노드 상세 다이어그램.
시작 노드 박스 안에 입력 필드 3개가 정의된 형태.
예: "email_draft (문단)", "recipient (짧은 텍스트)", "tone (선택: 격식체/친근한)"
각 필드 옆에 데이터 타입 표시] -->

8. 시작 노드에서 정의한 변수는 이후 노드의 프롬프트 안에 `{{변수명}}` 형태로 삽입된다. 예를 들어 LLM 노드의 프롬프트 안에 `{{email_draft}}`를 넣으면, 사용자가 입력한 이메일 초안이 그 자리에 자동으로 채워진다. 2편에서 다룬 프롬프트 템플릿이 여기서 실제로 작동하는 구조다.

---

## 4. LLM 노드: AI가 처리하는 단계

9. LLM 노드는 입력받은 데이터를 프롬프트에 따라 처리해서 결과물을 만드는 곳이다. 설정해야 할 항목은 세 가지다.

**모델 선택**
어떤 AI 엔진을 쓸지 결정한다. gpt-4o-mini는 비용과 성능의 균형이 좋아 일반 업무 자동화에 권장한다.

**프롬프트 작성**
2편에서 정리한 5원칙 구조로 작성한다. 변수는 `/` 키를 눌러 시작 노드에서 정의한 변수를 가져온다.

**출력 변수**
LLM의 결과물은 기본적으로 `text` 변수에 담긴다. 다음 노드에서 이 변수를 참조한다.

<!-- [이미지: LLM 노드 내부 구조 다이어그램.
LLM 노드 박스 안에 세 영역 표시:
위: "모델: gpt-4o-mini"
가운데: "프롬프트 (SYSTEM / USER 구분)"
아래: "출력 변수: text"
왼쪽에서 시작 노드 변수가 화살표로 프롬프트에 연결되는 형태] -->

10. LLM 노드를 여러 개 연결할 수 있다. 첫 번째 LLM 노드의 출력을 두 번째 LLM 노드의 입력으로 넣는 방식이다. 예를 들어 "1차 요약 → 2차 톤 조정"처럼 처리를 단계별로 나누면 각 단계의 품질을 독립적으로 관리할 수 있다.

---

## 5. 조건 분기: 흐름을 나누는 IF/ELSE

11. 모든 경우를 동일하게 처리할 수 없을 때 조건 분기를 쓴다. "긴급 문의면 A 처리, 일반 문의면 B 처리"처럼 입력의 특성에 따라 다른 흐름으로 보내는 것이다.

<!-- [이미지: 조건 분기 다이어그램.
"LLM 노드(카테고리 분류)" → "IF/ELSE 노드"에서 두 갈래로 분기.
위 화살표: "긴급 → LLM 노드(즉시 답변 생성)"
아래 화살표: "일반 → LLM 노드(표준 답변 생성)"
두 갈래가 다시 "출력 노드"로 합쳐지는 형태] -->

12. 조건 분기를 설계할 때 자주 하는 실수가 있다. 분기 전 단계에서 분류를 먼저 해야 한다는 것을 놓치는 것이다. IF/ELSE 노드는 조건을 판단하는 곳이지, 분류를 하는 곳이 아니다. 분류는 그 앞의 LLM 노드에서 처리하고, IF/ELSE 노드는 그 결과를 받아서 흐름만 나눈다.

```
[올바른 순서]
LLM 노드(입력을 읽고 카테고리를 판단해서 출력) 
→ IF/ELSE 노드(카테고리 변수 값에 따라 분기)

[잘못된 순서]
IF/ELSE 노드에서 직접 입력 텍스트를 분석하려는 시도
→ IF/ELSE는 텍스트를 읽지 못함. 변수 값만 비교 가능
```

---

## 6. 반복 처리: Iteration으로 리스트를 처리한다

13. 같은 처리를 여러 항목에 반복 적용해야 할 때 Iteration 노드를 쓴다. 예를 들어 10개의 고객 문의를 하나씩 읽고 각각 답변을 생성하거나, 5개의 뉴스 기사를 하나씩 요약하는 경우다.

<!-- [이미지: Iteration 노드 다이어그램.
"시작 노드(파일 리스트 입력)" → "Iteration 노드"
Iteration 노드 내부에 "LLM 노드(항목별 처리)" 표시.
오른쪽에 "반복 횟수: 리스트 길이만큼" 주석.
Iteration 노드 → "출력 노드(처리된 리스트 전체)" 연결] -->

14. Iteration과 조건 분기를 조합하면 복잡한 처리도 구조화할 수 있다. "리스트에서 항목을 하나씩 꺼내서 → 카테고리를 분류하고 → 카테고리에 따라 다른 처리를 적용한다"는 흐름이 대표적인 조합 패턴이다.

---

## 7. 출력 노드: 무엇을 내보낼지 결정한다

15. 출력 노드는 워크플로우 내부에서 만들어진 수많은 중간 결과물 중, 사용자에게 실제로 보여줄 것만 골라서 담는 곳이다. 출력 노드가 없으면 워크플로우는 "작업은 끝났는데 무엇을 내보낼지 모르는" 상태가 된다.

16. 출력 변수는 여러 개를 설정할 수 있다. 보고서 본문을 `report` 변수에 담고, 요약문을 `summary` 변수에 별도로 담아서 용도에 따라 다르게 활용하는 방식이다.

## 8. 실전: 이메일 교정 워크플로우 전체 설계

17. 지금까지 배운 노드를 조합해서 실제 워크플로우를 설계한다. 2편의 이메일 교정 프롬프트 템플릿을 그대로 활용한다.

<!-- [이미지: 이메일 교정 워크플로우 전체 다이어그램.
"시작 노드
  - email_draft (문단)
  - recipient (짧은 텍스트)
  - tone (선택: 격식체/친근한/전문적)"
→ "LLM 노드 1 (문법 및 맞춤법 교정)"
→ "LLM 노드 2 (tone에 맞게 어투 조정)"
→ "출력 노드
  - corrected_email
  - change_points"
각 노드 사이를 화살표로 연결하고 변수 흐름 표시] -->

**시작 노드 설정**
```
email_draft : 문단 (수정이 필요한 이메일 초안)
recipient   : 짧은 텍스트 (수신인 직급/관계)
tone        : 선택 (격식체 / 친근한 / 전문적)
```

**LLM 노드 1 프롬프트: 문법 교정**
```
# Role
당신은 한국어 문법 전문가입니다.

# Task
아래 이메일 초안의 문법, 맞춤법, 띄어쓰기를 교정하세요.
내용과 의미는 절대 변경하지 마세요.

# Input
{{email_draft}}

# Format
교정된 텍스트만 출력하세요. 설명 없이.
```

**LLM 노드 2 프롬프트: 톤 조정**
```
# Role
당신은 비즈니스 커뮤니케이션 전문가입니다.

# Task
아래 이메일을 {{tone}} 톤에 맞게 재작성하세요.
수신인은 {{recipient}}입니다.

# Input
{{llm_node_1.text}}

# Format
---
[교정된 이메일]
(최종 내용)
---
[수정 포인트]
- 개선 사항 2~3개를 bullet로 설명
```

18. 두 번째 LLM 노드의 입력에 `{{llm_node_1.text}}`를 넣은 것을 주목한다. 첫 번째 LLM 노드의 출력 변수를 그대로 참조하는 방식이다. 이렇게 노드 간 변수를 연결하면 처리 결과가 다음 단계로 자동으로 전달된다.

## 9. 자동화 가능 여부를 판단하는 기준

19. 모든 업무가 워크플로우로 자동화되는 것은 아니다. 기업 교육 현장에서 자동화 대상 업무를 선별할 때 쓰는 기준을 정리한다.

| 기준 | 자동화 적합 | 자동화 부적합 |
|---|---|---|
| 반복 빈도 | 매일/매주 반복 | 가끔 발생 |
| 단계 고정 여부 | 매번 같은 순서 | 상황마다 다름 |
| 판단 복잡도 | 명확한 기준 존재 | 맥락 의존적 판단 필요 |
| 입력 형태 | 텍스트, 파일 등 구조화 가능 | 대면 협의, 뉘앙스 중요한 작업 |

20. 자동화에 가장 먼저 적합한 업무 유형은 "반복되고, 단계가 고정되어 있고, 기준이 명확한 것"이다. 주간 보고서 초안 생성, 이메일 분류 및 답변 초안, 회의록 요약, 고객 문의 1차 분류가 대표적인 예다.

---

## 10. 정리

21. 워크플로우 설계는 도구 사용법이 아니라 사고법이다. 업무를 Input → Process → Output으로 분해하고, Process의 각 단계를 노드로 만들고, 노드 간 변수를 연결하는 것이 전부다. Dify는 이 사고의 결과를 캔버스 위에 시각화하는 수단이다.

22. 이 구조를 익히면 Dify가 아닌 다른 도구, 예를 들어 n8n이나 Make, LangChain을 써도 동일한 방식으로 설계할 수 있다. 도구가 바뀌어도 사고법은 그대로 적용된다.
