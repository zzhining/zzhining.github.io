"우리 회사 내규를 ChatGPT한테 물어봤더니 엉뚱한 말을 하더라고요."

1. 기업 AI 교육 현장에서 가장 많이 듣는 불만 중 하나다. 당연한 결과다. ChatGPT는 우리 회사 내규를 학습한 적이 없다. LLM은 학습 데이터에 있는 것만 안다. 없는 것은 모르거나, 더 나쁜 경우 그럴듯하게 지어낸다.

2. 이 문제를 해결하는 기술이 RAG(Retrieval-Augmented Generation)다. 번역하면 "검색 증강 생성"이다. AI가 답하기 전에 관련 문서를 먼저 검색해서 읽고 답하게 만드는 구조다. 6편에서는 RAG의 작동 원리부터 Dify에서 실제로 구현하는 방법까지 순서대로 정리한다.

---

## 1. LLM만 쓸 때의 두 가지 한계

3. RAG가 왜 필요한지를 이해하려면 LLM 단독 사용의 한계를 먼저 짚어야 한다.

**한계 1: 지식 단절(Knowledge Cutoff)**

LLM은 학습이 완료된 시점 이후의 정보를 모른다. 오늘 발표된 뉴스, 지난주에 개정된 내규, 이번 분기 실적 데이터를 물어봐도 답할 수 없다.

**한계 2: 할루시네이션(Hallucination)**

모르는 것을 모른다고 하지 않고 그럴듯하게 지어내는 현상이다. 사내 문서, 고객 데이터, 내부 프로세스처럼 학습 데이터에 없는 정보를 물어볼 때 특히 심하게 나타난다.

<!-- [이미지: LLM 한계 vs RAG 해결 비교 다이어그램.
왼쪽: "LLM 단독" - 사용자 질문이 LLM으로 직접 들어가고, LLM이 학습 데이터만으로 답하는 구조. "?" 표시와 함께 "최신 정보 없음 / 사내 데이터 없음" 주석.
오른쪽: "RAG" - 사용자 질문이 벡터DB로 먼저 가서 관련 문서를 찾고, 그 문서와 질문을 합쳐서 LLM에 전달하는 구조. "근거 기반 답변" 주석.] -->

4. RAG는 이 두 문제를 동시에 해결한다. 질문마다 관련 문서를 검색해서 LLM에 함께 전달하면, LLM은 학습 데이터 대신 그 문서를 근거로 답한다. 모르는 내용이 나오면 "문서에서 찾을 수 없습니다"라고 답하게 만들 수 있다.

## 2. RAG의 전체 흐름

5. RAG는 두 단계로 나뉜다. 문서를 미리 준비하는 **인덱싱** 단계와, 질문이 들어올 때마다 실시간으로 처리하는 **검색·생성** 단계다.

<!-- [이미지: RAG 전체 흐름 2단계 다이어그램.
상단 (인덱싱 단계, 1회): "문서 업로드 → 청킹(분할) → 임베딩(벡터화) → 벡터DB 저장"
하단 (검색·생성 단계, 매 질문마다): "사용자 질문 → 질문 임베딩 → 유사 청크 검색 → 프롬프트 조합 → LLM 답변 생성"
두 단계를 위아래로 구분하는 선과 함께 "사전 준비 (1회)" / "실시간 처리 (매번)" 레이블 표시.] -->

---

## 3. 인덱싱 1단계: 청킹 — 문서를 어떻게 자를 것인가

6. 문서를 LLM에 통째로 넣을 수 없다. 토큰 한도를 초과하기 때문이다. 그래서 문서를 작은 조각으로 나누는데, 이 과정을 청킹(Chunking)이라고 한다.

청킹의 핵심 설정값은 두 가지다.

- **청크 크기**: 한 조각의 최대 토큰 수. 권장값은 300~700 토큰
- **청크 오버랩**: 인접한 조각 간 겹치는 토큰 수. 권장값은 50~100 토큰

<!-- [이미지: 청킹 개념 다이어그램.
긴 문서가 여러 청크로 나뉘는 모습.
청크 1과 청크 2 사이에 "오버랩 구간(100 토큰)" 표시.
아래에 청크 크기 비교:
"너무 작음(100 토큰) → 문맥 손실"
"적정(500 토큰) → 문맥 유지"
"너무 큼(2000 토큰) → 검색 정밀도 하락"] -->

7. 오버랩이 필요한 이유가 있다. 중요한 정보가 청크 경계에 걸쳐 있을 수 있기 때문이다. 앞 청크 끝과 뒷 청크 시작 부분을 겹치게 저장해두면, 경계에서 문맥이 잘리는 문제를 줄일 수 있다.

**Dify 권장 청킹 설정**
```
청크 크기    : 500 토큰
청크 오버랩  : 100 토큰
분할 방식    : 재귀적 분할 (단락 → 문장 → 단어 순서로 시도)
```

---

## 4. 인덱싱 2단계: 임베딩 — 텍스트를 숫자로 변환한다

8. 청킹된 각 조각을 숫자 배열(벡터)로 변환하는 과정이 임베딩이다. 임베딩 모델이 텍스트를 수백~수천 개의 숫자로 표현한다. 의미가 비슷한 텍스트는 숫자 공간에서도 가까운 위치에 놓인다.

```
"환불 정책이 어떻게 되나요?" → [0.23, -0.45, 0.78, 0.12, ...]
"구매 취소는 어떻게 하죠?"   → [0.21, -0.43, 0.76, 0.14, ...]
← 두 문장의 벡터가 매우 가까움

"회사 창립연도는?"           → [-0.67, 0.34, -0.21, 0.89, ...]
← 위 두 문장과 벡터가 멀리 떨어짐
```

<!-- [이미지: 임베딩 벡터 공간 개념 다이어그램.
2차원 좌표계.
"환불 정책" 점과 "구매 취소" 점이 가까이 모여 있음.
"회사 창립연도" 점이 멀리 떨어져 있음.
"의미가 유사할수록 거리가 가까움" 주석 표시.] -->

9. 임베딩 모델 선택 시 반드시 지켜야 할 규칙이 하나 있다.

> **인덱싱할 때 쓴 임베딩 모델과 검색할 때 쓰는 임베딩 모델이 반드시 동일해야 한다.**

다른 모델을 쓰면 벡터 공간이 달라져서 검색 결과가 완전히 엉뚱하게 나온다.

**Dify 권장 임베딩 모델**
```
text-embedding-3-small : 비용·속도·품질 균형 최적. 일반 업무 권장
text-embedding-3-large : 높은 정확도 필요 시
BGE-M3 (로컬)          : 한국어 강점. 오픈 모델 환경에서 무료 사용 가능
```

## 5. 검색 단계: 질문과 가장 유사한 청크를 찾는다

10. 사용자가 질문을 입력하면 동일한 임베딩 모델로 질문도 벡터로 변환한다. 그리고 벡터DB에 저장된 수많은 청크 중에서 이 질문 벡터와 가장 가까운 것들을 골라온다.

<!-- [이미지: 검색 단계 다이어그램.
"사용자 질문 → 임베딩 모델 → 질문 벡터"
"벡터DB의 청크들" 중에서 질문 벡터와 가장 가까운 3~5개가 선택됨.
선택된 청크들이 "검색 결과"로 표시됨.
"Top K = 5" 주석 표시.] -->

핵심 파라미터 두 가지를 설정해야 한다.

| 파라미터 | 역할 | 권장값 |
|---|---|---|
| Top K | 가져올 청크 수 | 3~5 |
| Score Threshold | 최소 유사도 점수 | 0.5~0.7 |

11. Score Threshold를 너무 높게 설정하면 아무것도 검색되지 않는다. 처음에는 0.5로 시작해서 결과를 보면서 조정한다. Top K는 높을수록 더 많은 정보를 LLM에 제공하지만 토큰 비용도 올라간다.

**검색 전략 선택**

Dify는 세 가지 검색 전략을 제공한다.

```
Vector Search    : 벡터 유사도만 사용. 의미 기반 검색에 강함
Full-text Search : 키워드 매칭. 고유명사·코드·제품명 검색에 강함
Hybrid Search    : 두 방식을 혼합. 가장 안정적. 실무 권장
```

## 6. 생성 단계: 검색 결과를 LLM에 전달한다

12. 검색된 청크들은 LLM의 프롬프트에 "참고 자료"로 삽입된다. LLM은 자신의 학습 데이터가 아닌, 이 참고 자료를 근거로 답한다.

**RAG 프롬프트 구조**

```
# Role
당신은 사내 문서를 기반으로 답변하는 어시스턴트입니다.

# Instructions
- 반드시 아래 [참고 자료]의 내용만 사용해서 답변하세요.
- [참고 자료]에서 답을 찾을 수 없다면
  "제공된 문서에서 관련 정보를 찾을 수 없습니다"라고 답하세요.
- 답변 뒤에 출처 번호를 명시하세요. 예: [문서 1]

# 참고 자료
{{knowledge_retrieval_result}}

# 사용자 질문
{{user_query}}
```

13. 프롬프트에서 가장 중요한 한 줄은 이것이다.

> "참고 자료에서 답을 찾을 수 없다면 모른다고 답하세요."

이 한 줄이 없으면 LLM은 참고 자료에 없는 내용도 학습 데이터를 기반으로 지어낸다. 할루시네이션을 막는 핵심 장치다.

## 7. Dify에서 RAG 워크플로우 구현하기

14. Dify에서 RAG 파이프라인은 4개 노드로 완성된다.

<!-- [이미지: Dify RAG 워크플로우 전체 노드 다이어그램.
"시작 노드 (query 변수 입력)"
→ "Knowledge Retrieval 노드 (벡터DB 검색)"
→ "LLM 노드 (검색 결과 + 질문 → 답변 생성)"
→ "출력 노드 (최종 답변 반환)"
각 노드 사이 화살표 위에 전달되는 변수 표시:
시작→KR: "query"
KR→LLM: "retrieval_result"
LLM→출력: "text"] -->

**STEP 1. Knowledge Base 생성**

```
Knowledge 메뉴 → Create Knowledge
→ 문서 업로드 (PDF, DOCX, TXT, CSV 지원)
→ 청크 크기: 500 / 오버랩: 100
→ 임베딩 모델: text-embedding-3-small
→ Save & Process
```

**STEP 2. Knowledge Retrieval 노드 설정**

```
노드 추가 → Knowledge Retrieval 선택
→ Knowledge Base: 앞서 만든 KB 선택
→ Query Input: 시작 노드의 query 변수 연결
→ Search Mode: Hybrid Search
→ Top K: 5 / Score Threshold: 0.5
```

**STEP 3. LLM 노드 프롬프트 설정**

```
모델: gpt-4o-mini
SYSTEM 프롬프트:
  "당신은 사내 문서를 기반으로 답변하는 어시스턴트입니다.
   반드시 아래 참고 자료만 사용하세요.
   참고 자료에 없으면 모른다고 답하세요."

USER 프롬프트:
  참고 자료: {{knowledge_retrieval.result}}
  질문: {{sys.query}}
```

**STEP 4. 출력 노드 연결**

```
출력 변수: answer = LLM 노드의 text 변수
```

## 8. Doc Extractor vs Knowledge Retrieval: 언제 무엇을 쓰는가

15. Dify에서 문서를 AI에 연결하는 방법은 두 가지다. 상황에 따라 선택한다.

| 상황 | 선택 | 이유 |
|---|---|---|
| 파일 1개, 10페이지 이하 | Doc Extractor | 설정 없이 빠르게 처리 가능 |
| 파일 여러 개 또는 대용량 | Knowledge Retrieval (RAG) | 토큰 절약, 관련 부분만 추출 |
| 문서가 자주 업데이트됨 | Knowledge Retrieval (RAG) | 문서 교체만으로 즉시 반영 |
| 문서 전체 내용이 필요함 | Doc Extractor | RAG는 일부만 검색하므로 부적합 |

<!-- [이미지: Doc Extractor vs Knowledge Retrieval 비교 다이어그램.
왼쪽: "Doc Extractor" - 문서 전체가 LLM으로 한 번에 들어가는 구조. "간단하지만 대용량 부적합" 주석.
오른쪽: "Knowledge Retrieval" - 문서가 청크로 나뉘어 벡터DB에 저장되고, 관련 청크만 선택적으로 LLM에 전달되는 구조. "토큰 효율적, 대용량 가능" 주석.] -->

## 9. 자주 겪는 문제와 해결법

16. RAG를 처음 구현할 때 마주치는 문제 네 가지와 해결 방법을 정리한다.

**문제 1: 검색 결과가 엉뚱하다**
```
원인: 청크 크기가 너무 크거나, 임베딩 모델이 한국어에 약함
해결: 청크 크기를 300으로 줄이거나, BGE-M3 한국어 모델 사용
```

**문제 2: 아무것도 검색되지 않는다**
```
원인: Score Threshold가 너무 높음
해결: 0.3까지 낮춰서 테스트. 정상 검색되면 0.5로 복귀
```

**문제 3: 여전히 할루시네이션이 발생한다**
```
원인: 프롬프트에 "참고 자료 외 사용 금지" 지시가 없음
해결: 시스템 프롬프트에 "참고 자료에 없으면 모른다고 답하세요" 명시
```

**문제 4: 한국어 검색 품질이 영어보다 낮다**
```
원인: text-embedding-3-small이 한국어에 상대적으로 약함
해결: BGE-M3 또는 한국어 특화 임베딩 모델로 전환
```

## 10. 정리

17. RAG는 "AI가 답하기 전에 참고 자료를 먼저 찾아 읽게 만드는 구조"다. 인덱싱(청킹 → 임베딩 → 벡터DB 저장)을 한 번 해두면, 이후 모든 질문에 대해 자동으로 관련 문서를 검색해서 근거 기반 답변을 생성한다.

18. RAG 품질을 결정하는 세 가지 핵심 변수는 청킹 설정, 임베딩 모델 선택, 프롬프트의 "모른다고 답하라" 지시다. 이 세 가지를 제대로 설정하면, 사내 문서 기반 Q&A 챗봇의 신뢰도가 눈에 띄게 달라진다.
