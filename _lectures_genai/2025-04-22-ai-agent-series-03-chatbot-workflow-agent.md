"AI 자동화를 도입하고 싶다"는 말을 기업 교육 현장에서 자주 듣는다. 그런데 막상 어떤 구조로 만들어야 하는지 모르는 경우가 대부분이다. 챗봇을 만들어야 하는지, 워크플로우가 맞는지, 아니면 에이전트가 필요한지 기준이 없기 때문이다.

1. 세 구조를 구분하는 가장 명확한 기준은 하나다. **"판단 주체가 누구인가"**. 사람이 판단하는가, 시스템이 미리 짜둔 로직이 판단하는가, AI가 스스로 판단하는가. 이 기준으로 정리하면 세 구조의 차이가 선명하게 보인다.

## 1. 세 구조 한눈에 비교

## 2. 챗봇: 가장 단순한 구조

2. 챗봇은 "사용자 질문 → LLM → 답변"의 단순 왕복 구조다. 시스템 프롬프트로 AI의 역할과 말투를 정해두고, 사용자가 질문하면 그에 맞는 답을 돌려준다.

**챗봇이 적합한 업무**
- 자주 묻는 질문(FAQ) 자동 응답
- 특정 문서나 매뉴얼 기반 안내
- 고객 상담 1차 대응

3. 챗봇의 핵심 한계는 **대화 밖의 행동을 할 수 없다**는 것이다. 답변을 생성하는 것 이상의 작업, 예를 들어 외부 데이터를 검색하거나, 특정 조건에 따라 다른 처리를 하거나, 결과물을 파일로 저장하는 일은 챗봇 단독으로는 불가능하다.

<!-- [이미지: Dify 챗봇 구조 스크린샷 또는 다이어그램.
"시스템 프롬프트(역할 정의) → 사용자 입력 → LLM → 답변 출력" 단순 흐름] -->

## 3. 워크플로우: 로직을 설계자가 미리 짠다

4. 워크플로우는 처리 단계를 설계자가 미리 정의해둔 구조다. "A가 들어오면 B를 하고, B의 결과를 C에 넘기고, C의 결과를 출력한다"는 흐름이 고정되어 있다. AI는 각 단계에서 지정된 작업만 수행한다. 다음에 무엇을 할지 AI가 스스로 판단하지 않는다.

<!-- [이미지: 워크플로우 노드 흐름 다이어그램.
"시작 노드(입력 받기) → LLM 노드(1차 분석) → 조건 분기(IF/ELSE) → LLM 노드(결과 생성) → 출력 노드"
각 노드 사이를 화살표로 연결. 조건 분기에서 두 갈래 화살표 표시] -->

5. 워크플로우가 적합한 업무는 세 가지 특성을 가진다.

- **단계가 고정되어 있다**: 매번 같은 순서로 처리해도 되는 업무
- **일관성이 중요하다**: 담당자가 바뀌어도 같은 품질이 나와야 하는 업무
- **반복 빈도가 높다**: 매일, 매주 같은 작업을 처리해야 하는 업무

**워크플로우가 적합한 실무 예시**
```
예시 1. 이메일 교정 자동화
입력(초안) → LLM(문법 교정) → LLM(톤 조정) → 출력(교정본)

예시 2. 주간 보고서 생성
입력(원시 데이터) → LLM(데이터 분석) → LLM(리포트 작성) → 출력(보고서)

예시 3. 고객 문의 분류
입력(문의 내용) → LLM(카테고리 분류) → 조건 분기(카테고리별 처리) → 출력(담당 팀 전달)
```

6. 워크플로우의 강점은 **예측 가능성**이다. 같은 입력에 대해 항상 같은 흐름으로 처리한다. 기업 환경에서 AI 도입 초기에 가장 먼저 적용하기 좋은 구조가 워크플로우인 이유다.

---

## 4. 에이전트: AI가 스스로 판단한다

7. 에이전트는 워크플로우와 근본적으로 다르다. 설계자가 단계를 미리 정해두지 않는다. 대신 AI에게 목표와 사용 가능한 도구를 주고, 어떤 도구를 어떤 순서로 쓸지는 AI가 스스로 판단하게 한다.

에이전트의 구성 요소는 세 가지다.

- **두뇌(LLM)**: 상황을 이해하고 다음 행동을 결정
- **손발(Tools)**: 웹 검색, API 호출, 코드 실행 등 실제 행동 수단
- **기억(Memory)**: 이전 대화와 중간 결과를 저장해 문맥 유지

<!-- [이미지: 에이전트 루프 다이어그램.
"사용자 입력 → LLM 판단(Thought) → 도구 선택(Action) → 도구 실행 결과(Observation) → LLM 재판단 → ... → 최종 답변"
원형 또는 나선형 루프 구조로 표시. ReAct 사이클임을 명시] -->

8. 에이전트의 판단 루프를 ReAct라고 부른다. Reasoning(추론)과 Acting(행동)의 합성어다.

```
Thought: "이 주제에 대한 최신 정보가 필요하다. Tavily로 검색해야겠다."
Action: Tavily.search("2025 생성 AI 트렌드")
Observation: "검색 결과 5개 반환됨. 논문도 필요할 것 같다."
Thought: "ArXiv에서 관련 논문도 찾아보자."
Action: ArXiv.search("AI agent 2025")
Observation: "논문 3편 확인됨. 충분한 정보가 모였다."
Final Answer: "수집된 정보를 바탕으로 리포트를 작성한다."
```

9. 에이전트는 유연하지만 그만큼 관리가 필요하다. 같은 질문에도 매번 다른 도구를 선택할 수 있고, 반복 횟수가 늘어날수록 비용이 올라간다. 기업 실무에 도입할 때 반드시 최대 반복 횟수(Max Iterations)를 설정해야 하는 이유다.

## 5. 세 구조를 어떻게 선택하는가

10. 실무에서 구조를 선택할 때 쓰는 판단 기준을 정리한다.

<!-- [이미지: 구조 선택 플로우차트.
질문1: "단계가 고정되어 있는가?" → Y: "워크플로우"
질문2: "실시간 외부 정보가 필요한가?" → Y: "에이전트 고려"
질문3: "단순 Q&A로 충분한가?" → Y: "챗봇"
화살표로 연결된 의사결정 트리 형태] -->

```
Step 1. 업무의 단계가 매번 동일한가?
  → Yes: 워크플로우
  → No: Step 2로

Step 2. AI가 상황에 따라 다른 도구를 선택해야 하는가?
  → Yes: 에이전트
  → No: Step 3으로

Step 3. 단순 질의응답으로 해결되는가?
  → Yes: 챗봇
  → No: 워크플로우 + 에이전트 조합 고려
```

11. 기업 교육 현장에서 가장 많이 보는 실수는 두 가지다. 하나는 모든 것을 에이전트로 만들려는 것이고, 다른 하나는 챗봇으로 해결하려다 한계에 막히는 것이다. 에이전트는 강력하지만 비용이 높고 결과가 불안정하다. 반복 정형 업무는 워크플로우로 먼저 해결하고, 워크플로우로 처리하기 어려운 복잡한 판단이 필요한 부분에만 에이전트를 적용하는 것이 현실적이다.

## 6. 실무 조합 패턴

12. 세 구조는 서로 배타적이지 않다. 실제 업무 자동화는 세 구조를 조합해서 설계하는 경우가 많다.

<!-- [이미지: 조합 패턴 다이어그램.
패턴 1: "챗봇(사용자 입력 받기) → 워크플로우(정해진 단계 처리) → 출력"
패턴 2: "워크플로우(데이터 전처리) → 에이전트(복잡한 판단) → 워크플로우(결과 포매팅) → 출력"
두 패턴을 나란히 표시] -->

**패턴 1: 챗봇 + 워크플로우**
사용자가 챗봇 인터페이스로 요청을 입력하면, 내부에서 워크플로우가 정해진 단계로 처리한다. 사용자는 대화하는 느낌이지만, 실제 처리는 구조화된 파이프라인이 담당한다.

**패턴 2: 워크플로우 + 에이전트**
전처리와 후처리는 워크플로우로 고정하고, 판단이 필요한 핵심 단계에만 에이전트를 배치한다. 비용은 줄이고 유연성은 확보하는 구조다.

---

## 7. 정리

13. 세 구조의 핵심 차이를 한 문장씩 정리한다.

- **챗봇**: 사용자가 질문하면 AI가 답한다. 그것이 전부다.
- **워크플로우**: 설계자가 미리 짜둔 흐름을 AI가 단계별로 실행한다.
- **에이전트**: AI가 목표를 받고, 어떻게 달성할지 스스로 판단하며 행동한다.

14. 업무 자동화를 설계할 때 "어떤 AI 도구를 쓸까"보다 "이 업무의 판단 주체를 누구로 할 것인가"를 먼저 생각해야 한다. 그 질문의 답이 구조를 결정하고, 구조가 결정되면 도구는 자연스럽게 따라온다.
