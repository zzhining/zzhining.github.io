오늘은 **AI 모델 서빙 아키텍처**를 이야기합니다.

---

1. 좋은 모델을 만들었다고 좋은 서비스가 되는 게 아닙니다. **서빙 아키텍처가 잘못되면** 아무리 정확한 모델도 느리고, 비싸고, 불안정한 서비스가 됩니다.

2. **모델 서빙**이란 학습된 AI 모델을 실제 사용자 요청에 응답할 수 있도록 배포하고 운영하는 과정입니다. 모델 개발이 레시피를 만드는 일이라면, 서빙은 실제 주방에서 음식을 만들어 손님에게 내는 일입니다.

3. 서빙 방식에는 크게 세 가지가 있습니다. **REST API 추론, 배치 추론, 스트리밍 추론**. 어떤 방식을 선택하느냐에 따라 사용자 경험, 비용, 인프라 구조가 완전히 달라집니다.

4. **REST API 추론**은 사용자 요청이 들어오는 즉시 모델이 응답하는 방식입니다. 챗봇, 추천 시스템처럼 실시간 응답이 필요한 서비스에 적합합니다. 응답 속도가 핵심 지표이며, 지연 시간이 길어지면 사용자가 이탈합니다.

5. **배치 추론**은 요청을 모아서 한꺼번에 처리하는 방식입니다. 대량의 데이터를 주기적으로 분석하거나, 응답 속도보다 처리량이 중요한 업무(리포트 생성, 이메일 분류, 대규모 문서 처리)에 적합합니다. REST API보다 훨씬 저렴하게 운영할 수 있습니다.

6. **스트리밍 추론**은 결과를 한 번에 전달하지 않고 생성되는 즉시 순차적으로 전달하는 방식입니다. ChatGPT처럼 글자가 하나씩 나타나는 경험이 이것입니다. 사용자가 전체 결과를 기다리는 체감 시간을 줄여 줍니다.

7. 기획자가 결정해야 하는 첫 번째 질문입니다. **"우리 AI 서비스의 응답이 얼마나 빠르게 나와야 하는가."** 이 질문에 답하지 못하면 개발팀은 아키텍처를 설계할 수 없습니다.

8. 응답 속도 요건은 서비스 유형마다 다릅니다. **대화형 서비스**는 3초 이내가 기준선, **검색 보조**는 1초 이내, **배치 분석 리포트**는 수 분이어도 무방합니다. 기획자가 이 기준을 명시해야 합니다.

9. 응답 속도, 처리량, 비용은 **트레이드오프 관계**입니다. 빠른 응답을 원하면 고성능 GPU를 상시 가동해야 하고, 비용이 올라갑니다. 비용을 줄이면 응답이 느려지거나 처리량이 줄어듭니다. 세 가지를 동시에 최적화하는 마법은 없습니다.

10. **GPU 비용**은 AI 서비스 운영의 핵심 변수입니다. GPU를 항상 켜두는 방식(전용 인스턴스)과 요청이 있을 때만 켜는 방식(서버리스)의 비용 차이는 수십 배에 달합니다. 사용 패턴에 맞는 선택이 필요합니다.

11. **오토스케일링**은 트래픽 급증에 대비하는 구조입니다. 평소에는 서버를 적게 유지하다가 요청이 몰리면 자동으로 늘리는 방식입니다. 설정을 잘못하면 트래픽이 몰릴 때 응답이 폭발적으로 느려집니다.

12. **모델 경량화**는 속도와 비용 문제를 동시에 해결하는 방법입니다. 모델의 정밀도를 낮추거나 크기를 줄여 같은 하드웨어에서 더 빠르게, 더 저렴하게 추론할 수 있게 합니다. 기획자는 경량화로 인한 성능 저하를 감수할 수 있는지 판단해야 합니다.

13. 기획자가 아키텍처 회의에서 반드시 확인해야 할 것이 있습니다. **SLA(서비스 수준 협약)** — 응답 시간 목표, 가용성 목표(99.9%면 연간 약 8.7시간 다운), 장애 대응 시간. 이 수치가 없는 서비스 설계는 무책임합니다.

14. **캐싱 전략**은 반복 요청 비용을 대폭 줄여 줍니다. 동일하거나 유사한 질문에 이미 생성된 답변을 재사용하는 방식입니다. 자주 묻는 질문이 많은 서비스에서는 캐싱만으로 API 비용을 40~60% 절감할 수 있습니다.

15. 서빙 아키텍처 결정은 출시 후 바꾸기 어렵습니다. **처음 설계할 때 비즈니스 요구사항을 명확히 반영하지 않으면** 나중에 전면 재구축이 필요한 상황이 옵니다. 기획자가 기술 결정에 참여해야 하는 이유가 여기 있습니다.

---

**마무리**

1. AI 서비스 기획서에는 응답 속도 목표, 월 예상 요청 건수, 허용 비용 범위가 명시되어야 합니다. 이 세 가지가 없으면 개발팀은 어떤 아키텍처도 결정할 수 없습니다.

2. REST API, 배치, 스트리밍 중 무엇을 쓸지는 서비스 시나리오를 보면 결정됩니다. 기획자가 시나리오를 명확히 정의해야 개발팀이 올바른 선택을 할 수 있습니다.

3. 비용 대비 성능의 트레이드오프는 기술팀이 아니라 비즈니스 책임자가 결정해야 합니다. 기획자가 그 결정을 회피하면 개발팀이 임의로 선택하게 됩니다.
