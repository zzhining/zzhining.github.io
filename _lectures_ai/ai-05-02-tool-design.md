오늘은 **AI 도구 설계와 Function Calling**을 이야기합니다.

---

1. **AI 에이전트가 강해지는 이유는 단 하나**입니다. 말만 하던 AI가 '행동'을 할 수 있게 됐기 때문입니다. 텍스트를 생성하는 것과 실제로 시스템을 건드리는 것은 완전히 다른 이야기입니다. 도구를 쥐어주는 순간 AI는 비서가 됩니다.

2. **Function Calling**은 AI가 미리 정의된 함수를 호출할 수 있도록 하는 기술입니다. AI 모델이 "지금 날씨 검색이 필요하다"고 판단하면, 직접 검색 API를 호출합니다. 사람이 중간에 끼지 않아도 됩니다. 2023년 OpenAI가 GPT에 도입하면서 업계 표준이 됐습니다.

3. **도구란 AI가 외부 세계와 상호작용하는 모든 수단**입니다. 인터넷 검색, 데이터베이스 조회, 이메일 발송, 캘린더 예약, 파일 생성, 외부 API 호출이 모두 도구입니다. AI는 혼자 아무것도 못 하지만, 도구가 생기면 무엇이든 할 수 있습니다.

4. **Function Calling의 작동 방식은 생각보다 단순합니다.** 기획자나 개발자가 "이런 도구가 있다"고 AI에게 미리 알려줍니다. AI는 대화 흐름 중 필요한 순간에 그 도구를 선택해 호출합니다. 결과를 받아 다시 사용자에게 답합니다. 이 루프가 에이전트의 핵심입니다.

5. **기획자의 역할은 "어떤 도구를 줄 것인가"를 결정하는 것**입니다. 개발자는 도구를 만들지만, 어떤 도구가 비즈니스에 필요한지는 기획자가 정의해야 합니다. 도구 목록이 곧 AI의 능력 범위입니다. 목록을 잘못 짜면 AI는 아무 쓸모가 없거나 위험해집니다.

6. **도구 설계의 첫 번째 원칙은 '최소 권한'**입니다. AI에게 필요한 도구만 줘야 합니다. 고객 응대 AI에게 데이터베이스 삭제 권한을 줄 이유가 없습니다. 권한이 많을수록 사고의 범위도 넓어집니다. 처음엔 좁게 시작하고, 필요할 때 늘리세요.

7. **도구 설명(Description)은 AI가 읽는 명세서**입니다. 개발자가 함수를 코딩하는 것보다 도구 설명을 잘 쓰는 것이 더 중요할 때가 있습니다. AI는 이름과 설명을 보고 "지금 이 도구를 써야 한다"고 판단합니다. 모호한 설명은 엉뚱한 호출을 만듭니다.

8. **도구 이름 하나에도 설계 철학이 담겨 있습니다.** `get_user_data`보다 `get_customer_purchase_history`가 낫습니다. 범용적인 이름은 AI를 혼란스럽게 합니다. 도구가 무엇을 하는지 이름만 봐도 알 수 있어야 합니다. 이건 사람을 위한 것이 아니라 AI를 위한 작업입니다.

9. **도구가 너무 많으면 AI가 선택 장애에 빠집니다.** 한 번의 대화에서 AI가 선택할 수 있는 도구가 20개를 넘으면 정확도가 떨어집니다. 맥락에 맞는 도구 세트를 상황별로 다르게 구성하는 것이 실무 전략입니다. 기획 단계에서 도구 그룹핑까지 고민해야 합니다.

10. **보안 사고는 대부분 도구 설계 실수에서 납니다.** AI가 이메일 발송 도구를 가지고 있을 때, 누군가 "모든 고객에게 메일 보내줘"라고 입력하면 어떻게 됩니까. 도구 자체에 제약 조건을 넣지 않으면 AI는 요청대로 실행합니다. 도구 설계 단계에서 남용 시나리오를 반드시 검토해야 합니다.

11. **읽기 도구와 쓰기 도구는 완전히 다른 리스크를 가집니다.** 데이터를 조회하는 도구는 최악의 경우 정보 유출입니다. 데이터를 수정하거나 삭제하는 도구는 복구 불가능한 사고로 이어집니다. 쓰기 도구에는 반드시 확인 단계와 롤백 방안을 설계하세요.

12. **도구 호출 로그는 반드시 남겨야 합니다.** AI가 어떤 도구를 언제 왜 호출했는지 추적할 수 없으면 문제가 생겼을 때 원인을 찾을 수 없습니다. 로그는 성능 개선의 데이터이기도 합니다. "AI가 이 도구를 자주 쓰는구나"는 사용자 니즈를 읽는 신호입니다.

13. **도구 실패 처리는 기획서에 들어가야 할 내용**입니다. 외부 API가 죽으면 AI는 어떻게 행동해야 합니까. 그냥 에러를 내놓을 것인지, 대체 경로로 갈 것인지, 사용자에게 어떻게 안내할 것인지. 이걸 기획하지 않으면 UX가 망가집니다.

14. **Parallel Tool Use는 속도의 핵심**입니다. AI가 여러 도구를 동시에 호출할 수 있으면 처리 속도가 획기적으로 빨라집니다. 날씨 조회와 교통 정보를 순서대로 가져올 이유가 없습니다. 병렬 호출 설계는 에이전트 응답 속도를 직접적으로 결정합니다.

15. **도구 설계는 비즈니스 전략입니다.** 어떤 도구를 AI에게 주느냐가 AI가 어떤 가치를 만들어내느냐를 결정합니다. 경쟁사와 같은 AI 모델을 쓰더라도 도구 설계가 뛰어나면 훨씬 강력한 서비스가 됩니다. 기술이 아니라 기획의 문제입니다.

---

**마무리**

1. 도구는 많을수록 좋은 것이 아닙니다. AI에게 필요한 도구만, 최소 권한으로, 명확한 설명과 함께 줘야 합니다. 도구 목록이 곧 AI의 능력과 리스크를 동시에 정의합니다.

2. 보안 사고는 도구 설계 단계에서 막아야 합니다. 도구가 완성된 이후에 보안을 고민하면 늦습니다. 특히 쓰기 권한이 있는 도구는 남용 시나리오를 기획 단계에서 반드시 검토하세요.

3. 좋은 도구 설계는 좋은 기획서에서 나옵니다. Function Calling은 개발자의 영역처럼 보이지만, 어떤 도구를 만들고 어떻게 설명할지는 기획자의 몫입니다. AI 기획자의 경쟁력은 여기서 갈립니다.
