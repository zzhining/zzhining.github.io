오늘은 **AI 에이전트 평가와 디버깅**을 이야기합니다.

---

1. 에이전트는 일반 AI 모델과 다릅니다. **단일 응답**이 아니라 여러 단계를 거쳐 목표를 수행합니다. 그만큼 오류가 쌓이고 증폭될 기회가 많습니다.

2. 일반 챗봇은 질문 하나에 답변 하나입니다. 에이전트는 **10단계 추론과 3번의 도구 호출** 끝에 결과를 냅니다. 첫 단계 오류는 마지막 단계까지 전파됩니다.

3. "에이전트가 이상하게 작동한다"는 민원이 들어왔을 때, 어디서 잘못됐는지 찾지 못하면 고칠 수 없습니다. **추적 가능성(Observability)**이 에이전트 운영의 전제 조건입니다.

4. 에이전트 평가에는 **세 가지 수준**이 있습니다. 개별 단계 정확도, 전체 태스크 완료율, 최종 비즈니스 목표 달성율. 이 세 가지를 구분하지 못하면 "에이전트가 잘 작동하고 있다"는 말의 의미가 없습니다.

5. **태스크 완료율**만 보는 건 위험합니다. 에이전트가 태스크를 '완료'했더라도 결과물의 품질이 기준 미달이면 무의미합니다. 완료와 정확을 반드시 구분해야 합니다.

6. 에이전트 실패는 크게 세 유형입니다. **무한 루프**(같은 단계를 반복), **잘못된 도구 선택**(적합하지 않은 API 호출), **맥락 소실**(대화 흐름을 잃고 엉뚱한 방향으로 진행). 이 세 가지에 대한 감지 로직을 처음부터 설계해야 합니다.

7. **실패 시나리오 목록**은 에이전트 설계서에 반드시 포함되어야 합니다. "이 에이전트가 실패할 수 있는 상황 10가지"를 쓰지 못하면 에이전트를 제대로 이해하지 못한 겁니다.

8. **Human-in-the-Loop(사람 개입 시점)**를 설계하는 것은 기획자의 역할입니다. 에이전트가 판단을 내리기 전에 사람이 확인해야 하는 상황을 미리 정의해야 합니다. 이걸 개발팀에 맡기면 안 됩니다.

9. 사람이 개입해야 하는 상황의 기준은 **리스크와 비용**입니다. 되돌릴 수 없는 행동(결제, 발송, 삭제)은 반드시 사람이 확인하는 단계를 둬야 합니다. "자동화니까 사람 개입은 안 돼"라는 생각이 사고를 만듭니다.

10. 에이전트 디버깅에는 **단계별 로그**가 필수입니다. 에이전트가 왜 그 도구를 선택했는지, 어떤 판단 근거로 다음 단계를 결정했는지 기록되어야 합니다. 로그 없는 에이전트는 블랙박스입니다.

11. **에이전트 테스트는 엔드-투-엔드**로 해야 합니다. 단위 테스트로 개별 도구가 작동함을 확인해도, 전체 흐름에서 에이전트가 올바른 도구를 올바른 순서로 쓰는지는 별개 문제입니다.

12. 에이전트 품질 지표를 보고서에 담아야 한다면 이 세 가지를 쓰십시오. **완료율, 오류율, 평균 처리 시간**. 이것 없이 "잘 되고 있어요"는 보고가 아닙니다.

13. **비용 폭발**은 에이전트의 대표적 실패 패턴입니다. 에이전트가 루프에 빠지면 API 호출이 기하급수로 늘어납니다. 최대 단계 수, 최대 비용 한도를 하드코딩하는 것이 필수 안전장치입니다.

14. **회귀 테스트 세트**를 만들어 두십시오. 에이전트를 업데이트할 때마다 이전에 잘 작동하던 시나리오가 깨지지 않았는지 자동으로 검증하는 체계가 없으면, 개선이 다른 부분을 망가뜨리는 사실을 뒤늦게 발견합니다.

15. 에이전트 평가 체계를 갖추는 데는 시간이 걸립니다. 하지만 이것 없이 에이전트를 운영하는 건 **핸들 없는 차를 도로에 내보내는 것**과 같습니다. 평가 설계가 먼저, 도입은 그다음입니다.

---

**마무리**

1. 에이전트 도입을 결정했다면 평가 지표와 실패 시나리오 목록을 먼저 만드십시오. 없으면 도입하지 마십시오.

2. Human-in-the-Loop 설계는 기획자의 업무입니다. 개발팀에 위임할 수 있는 영역이 아닙니다.

3. "에이전트가 잘 작동한다"는 말은 수치로 증명되어야 합니다. 완료율, 오류율, 처리 시간 — 이 세 가지가 없으면 그 말은 의미가 없습니다.
