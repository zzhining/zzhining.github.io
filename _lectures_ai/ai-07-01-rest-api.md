오늘은 **REST API 설계**를 이야기합니다.

---

1. AI 기능을 기존 서비스에 연결하는 방법은 **REST API**입니다. API는 두 시스템이 서로 대화하는 창구입니다. "이 텍스트를 분석해줘"라는 요청을 AI 서버에 보내고, AI 서버가 결과를 돌려주는 것 — 이 교환이 API를 통해 일어납니다.

2. 기획자가 API를 코드 수준까지 알 필요는 없습니다. 하지만 **API가 무엇인지, 어떻게 작동하는지**는 알아야 합니다. 개발 범위를 산정하고, 외부 AI 서비스 비용을 계획하고, 개발팀과 제대로 된 대화를 하려면 API 개념은 필수입니다.

3. AI 서비스를 구축할 때 두 가지 선택지가 있습니다. **직접 AI 모델을 만들어 API로 서빙**하거나, **OpenAI·Claude 같은 외부 AI API를 사용**하는 것입니다. 전자는 초기 투자가 크지만 통제권이 있고, 후자는 빠르지만 사용량에 따라 비용이 증가합니다.

4. 외부 AI API를 사용할 경우 **호출 비용**을 사전에 계획해야 합니다. 사용자 수, 평균 요청 횟수, 입출력 데이터 크기에 따라 월 비용이 수십만 원에서 수억 원까지 달라집니다. "API 호출 비용은 개발팀이 알아서 할 것"이라는 생각은 예산 폭발로 이어집니다.

5. API 설계에서 기획자가 반드시 결정해야 할 첫 번째 사항은 **응답 속도(레이턴시) 요구사항**입니다. 사용자가 AI 결과를 기다릴 수 있는 최대 시간은 몇 초인가. 이 기준이 없으면 개발팀은 비용 최적화된 느린 시스템을 만들 수 있습니다.

6. 일반적인 기준으로, 사용자가 직접 인터랙션하는 서비스는 **2초 이내** 응답이 필요합니다. 배치 처리나 백그라운드 작업은 수분이 허용됩니다. 응답 속도 요구사항이 높을수록 인프라 비용도 증가합니다. 이 트레이드오프를 기획 단계에서 명확히 해야 합니다.

7. 두 번째로 결정해야 할 것은 **인증(Authentication) 방식**입니다. 누가 이 API를 호출할 수 있는가. 내부 시스템만인가, 외부 파트너도 가능한가, 일반 사용자도 직접 호출할 수 있는가. 인증 방식에 따라 보안 수준과 개발 복잡도가 달라집니다.

8. 세 번째는 **비용 구조 설계**입니다. AI API 호출이 무제한으로 허용되면 악의적인 사용이나 버그 하나로 수천만 원이 청구될 수 있습니다. 사용자별 호출 한도, 일별 한도, 비용 경보 기준을 사전에 설정해야 합니다.

9. **동기(Synchronous) vs 비동기(Asynchronous)** 처리 방식도 기획 단계에서 결정해야 합니다. 동기 방식은 결과가 나올 때까지 기다립니다. 비동기 방식은 요청을 보내고 나중에 결과를 가져옵니다. AI 처리가 오래 걸리는 경우 비동기가 맞지만, 사용자 경험 설계가 복잡해집니다.

10. **에러 처리 시나리오**를 정의해야 합니다. AI API가 응답하지 않으면 서비스는 어떻게 동작하는가. AI 없이 기본 기능으로 대체(폴백)할 것인가, 에러 메시지를 보여줄 것인가, 재시도할 것인가. 이 결정이 없으면 개발팀은 각자 다르게 구현합니다.

11. 외부 AI API(예: OpenAI, Claude, Google AI)를 사용할 경우 **의존성 위험**을 고려해야 합니다. 해당 회사가 가격을 올리거나, API 정책을 바꾸거나, 서비스를 중단하면 우리 서비스에 직접 영향이 갑니다. 중요한 서비스라면 대체 API를 미리 검토해야 합니다.

12. API 버전 관리도 기획자가 이해해야 할 개념입니다. **AI 모델이 업그레이드되면 기존 API 응답 형식이 바뀔 수 있습니다.** 이것이 하위 호환성을 깨면 기존 서비스가 오동작합니다. 버전 관리 정책을 사전에 정해야 합니다.

13. **API 문서화**는 기획자가 요구해야 할 산출물입니다. 개발팀 내부 API든 외부 API든, 어떤 요청을 보내면 어떤 응답이 오는지를 명문화하지 않으면 유지보수와 기능 추가가 어려워집니다.

14. 기획자가 개발팀에 API 설계를 맡길 때 반드시 요구해야 할 것이 있습니다. **"이 API를 호출할 때 비용이 얼마나 발생하는가"를 명확히 산정해 달라는 것**입니다. 호출 횟수, 데이터 크기, 월간 예상 비용을 수치로 받아야 합니다.

15. REST API를 이해하는 기획자는 **개발팀과 다른 대화**를 합니다. "이 기능 붙여주세요"가 아니라 "이 기능의 API 응답속도 요구사항은 2초, 월 호출량은 100만 건, 에러 시 폴백은 기본 텍스트 출력으로 설정합시다"라고 말합니다. 이 차이가 프로젝트 성패를 가릅니다.

---

**마무리**

1. 기획자가 REST API를 알아야 하는 이유는 코드를 짜기 위해서가 아닙니다. 개발 범위를 정확히 산정하고, API 비용을 계획하고, 응답속도·인증·에러처리 같은 핵심 설계 결정을 내리기 위해서입니다.

2. 외부 AI API 사용 시 비용 구조, 의존성 위험, 버전 관리 정책은 기획 단계에서 반드시 검토해야 합니다. 이것을 놓치면 나중에 예산과 일정 모두 흔들립니다.

3. API 설계에서 기획자가 결정해야 할 핵심은 응답속도 요구사항, 인증 방식, 비용 한도 설정 — 이 세 가지입니다. 이것을 명확히 정의한 기획서가 좋은 기획서입니다.
