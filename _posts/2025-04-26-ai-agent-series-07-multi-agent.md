## "에이전트 하나로 다 시키면 안 되나요?"

가능하다. 하지만 좋지 않다. 
한 사람이 기획, 조사, 작성, 검수를 동시에 하면 각 단계의 품질이 낮아지는 것처럼, 
에이전트도 역할이 섞이면 결과의 품질과 신뢰도가 떨어진다. 멀티 에이전트는 이 문제를 해결하는 구조다.

이번 편에서는 단일 에이전트와 멀티 에이전트의 차이, 역할을 어떻게 나눌 것인지, 실무에서 쓸 수 있는 설계 패턴 두 가지를 정리한다. 

---

## 1. 단일 에이전트의 한계

단일 에이전트는 하나의 AI가 모든 도구를 직접 사용해서 처음부터 끝까지 처리한다. 
간단한 작업에는 단일 에이전트로 충분하다. 하지만 작업이 복잡해질수록 세 가지 문제가 드러난다.

**문제 1: 역할 혼선**

하나의 에이전트가 "리서치도 하고, 분석도 하고, 글도 써야" 한다. 
Instructions이 복잡해지고, AI가 지금 어떤 역할을 해야 하는지 혼동하기 시작한다.


**문제 2: 오류 전파**

리서치 단계에서 잘못된 정보를 가져왔을 때, 단일 에이전트는 그것을 검증하지 않고 그대로 글쓰기 단계로 넘긴다. 
초기 오류가 최종 결과물까지 전파된다.


**문제 3: 병렬 처리 불가**

단일 에이전트는 순서대로 처리한다. 
리서치가 끝나야 분석을 시작하고, 분석이 끝나야 작성을 시작한다. 
독립적으로 처리할 수 있는 작업도 직렬로 처리하므로 시간이 오래 걸린다.

<!-- [이미지: 단일 에이전트 vs 멀티 에이전트 비교 다이어그램.
왼쪽 (단일): 하나의 에이전트 박스에서 "리서치 → 분석 → 작성"이 직렬로 처리되는 구조. 오류 발생 시 화살표가 끝까지 이어지는 형태.
오른쪽 (멀티): 오케스트레이터 → 리서치 에이전트 / 분석 에이전트 / 작성 에이전트가 병렬로 배치된 구조. 각 에이전트가 독립적으로 처리하고 결과를 통합하는 형태.] -->

## 2. 멀티 에이전트의 핵심 원리

멀티 에이전트는 하나의 복잡한 목표를 역할이 다른 여러 에이전트에게 나눠서 처리하는 구조다. 
각 에이전트는 자신의 역할에만 집중한다. 역할이 명확할수록 각 단계의 품질이 올라간다.

멀티 에이전트 구조의 핵심은 `오케스트레이터`와 `실행 에이전트`이다.

**오케스트레이터(Orchestrator)**
전체 작업을 조율하는 관리자 역할이다. 
목표를 받아서 어떤 에이전트에게 어떤 작업을 맡길지 결정하고, 각 에이전트의 결과를 취합해서 최종 결과물로 만든다.

**실행 에이전트(Worker Agent)**
오케스트레이터로부터 구체적인 작업을 받아서 실행하는 역할이다. 
리서치 에이전트, 분석 에이전트, 작성 에이전트처럼 각자의 전문 영역만 담당한다.

## 3. 설계 패턴 1: 순차 처리형

가장 기본적인 멀티 에이전트 패턴이다. 앞 에이전트의 출력이 다음 에이전트의 입력이 된다. 
각 단계가 독립된 에이전트로 처리되므로, 각 단계에 최적화된 Instructions를 줄 수 있다.

![순차 처리형 패턴](/assets/image/ai-agent-07/sequential-pattern.png)
<!-- [이미지: 순차 처리형 패턴 다이어그램.
"시작 노드(주제 입력)"
→ "에이전트 노드 1: 리서치 에이전트 (Tavily + ArXiv로 정보 수집)"
→ "에이전트 노드 2: 분석 에이전트 (수집된 정보에서 핵심 인사이트 추출)"
→ "에이전트 노드 3: 작성 에이전트 (인사이트를 바탕으로 리포트 작성)"
→ "출력 노드 (최종 리포트)"
각 노드 사이 화살표 위에 전달 변수 표시.] -->

**실제 구현 흐름**

```
시작 노드
  입력 변수: topic (분석할 주제)

에이전트 노드 1 — 리서치 에이전트
  Instructions:
    주어진 주제에 대해 최신 정보를 수집하세요.
    주제: {{topic}}
    1. Tavily로 웹 검색 (2~3회)
    2. ArXiv에서 관련 논문 검색 (1회)
    3. 수집된 정보를 항목별로 정리해서 출력
  Tools: Tavily Search, ArXiv
  출력: research_result

에이전트 노드 2 — 분석 에이전트
  Instructions:
    아래 리서치 결과를 분석해서 핵심 인사이트 3가지를 도출하세요.
    리서치 결과: {{research_result}}
    각 인사이트에 근거가 되는 출처를 함께 명시하세요.
  출력: analysis_result

에이전트 노드 3 — 작성 에이전트
  Instructions:
    아래 분석 결과를 바탕으로 실무자용 리포트를 작성하세요.
    분석 결과: {{analysis_result}}
    형식: 요약(3줄) / 핵심 인사이트 / 시사점 / 출처
  출력: final_report

출력 노드
  출력 변수: final_report
```

이 패턴의 핵심은 각 에이전트의 Instructions이 단순하다는 것이다. 리서치 에이전트는 정보 수집만, 분석 에이전트는 인사이트 도출만, 작성 에이전트는 문서 생성만 담당한다. 역할이 명확할수록 각 단계의 결과 품질이 높아진다.

## 4. 설계 패턴 2: 병렬 처리형

독립적으로 처리 가능한 작업을 동시에 실행하는 패턴이다. 
Dify의 Parallel 노드를 활용한다. 순차 처리보다 전체 처리 시간이 단축된다.

<!-- [이미지: 병렬 처리형 패턴 다이어그램.
"시작 노드(주제 입력)"
→ "분기점 (Parallel)"
  왼쪽 분기: "국내 동향 리서치 에이전트"
  오른쪽 분기: "해외 동향 리서치 에이전트"
두 분기가 완료되면 → "병합점"
→ "통합 작성 에이전트 (국내 + 해외 결과 종합)"
→ "출력 노드"] -->

![병렬 처리형 패턴](/assets/image/ai-agent-07/parallel-pattern.png)
**병렬 처리가 적합한 경우**
```
- 국내 동향 조사 + 해외 동향 조사를 동시에 실행
- 여러 문서를 각각 요약한 뒤 통합
- 동일한 데이터를 다른 관점(재무 / 운영 / 마케팅)으로 동시 분석
```

병렬 처리형은 속도 이점이 있지만 주의할 점이 있다. 병렬로 실행된 에이전트들이 서로의 결과를 참조하지 못한다. 
한 에이전트의 결과가 다른 에이전트의 처리에 영향을 줘야 한다면 순차 처리형을 써야 한다.

## 5. Dify에서 멀티 에이전트 구현하기

Dify 워크플로우에서 에이전트 노드를 여러 개 연결하면 멀티 에이전트 구조가 완성된다. 
구현 전 반드시 확인할 사항이 하나 있다.

> **Agent Strategies 플러그인이 설치되어 있어야 에이전트 노드를 사용할 수 있다.**

<!-- [이미지: Dify 멀티 에이전트 워크플로우 캔버스 다이어그램.
"시작 노드"
→ "에이전트 노드 1 (리서치)"
  설정: Strategy: ReAct, Tools: Tavily+ArXiv, Max Iterations: 7
→ "에이전트 노드 2 (작성)"
  설정: Strategy: Function Calling, Max Iterations: 5
→ "출력 노드"
각 에이전트 노드 내부에 핵심 설정값 표시.
노드 간 연결 화살표 위에 전달 변수 표시.] -->

**에이전트 노드 핵심 설정값**

| 설정 항목 | 권장값 | 설명 |
|---|---|---|
| Agent Strategy | ReAct 또는 Function Calling | 5편 참고 |
| Model | gpt-4o-mini | 비용·성능 균형 |
| Tools | 역할별 필요한 도구만 | 도구가 많을수록 오류 가능성 증가 |
| Max Iterations | 5~10 | 역할이 단순할수록 낮게 설정 |
| Instructions | 단일 역할만 명시 | 역할 혼선 방지 핵심 |
| Query | 이전 노드 출력 변수 연결 | `{{이전_에이전트노드.output}}` |

## 6. 멀티 에이전트 설계 원칙

멀티 에이전트를 설계할 때 지켜야 할 원칙 세 가지를 정리한다.

**원칙 1: 역할은 하나씩**

에이전트 하나에 역할 하나다. 
"리서치도 하고 분석도 하는 에이전트"는 멀티 에이전트의 의미가 없다. 
Instructions을 작성할 때 **동사가 하나여야 한다.** "수집하세요", "분석하세요", "작성하세요"처럼.

**원칙 2: 인터페이스를 명확하게**

각 에이전트의 출력 형식을 명확하게 정의해야 한다. 
앞 에이전트의 출력이 다음 에이전트의 입력이 되기 때문이다. 
출력 형식이 모호하면 다음 에이전트가 입력을 제대로 해석하지 못한다.

```
나쁜 예: "수집한 정보를 정리해서 출력하세요."
좋은 예: "수집한 정보를 아래 형식으로 출력하세요.
          ## 출처별 핵심 내용
          - [출처명]: (핵심 내용 2줄)
          ## 공통 키워드"
```

**원칙 3: 오케스트레이터는 단순하게**

오케스트레이터의 역할은 "무엇을 누구에게 맡길지"를 결정하는 것뿐이다. 
오케스트레이터가 직접 처리까지 하려고 하면 단일 에이전트와 다를 것이 없어진다.

## 7. 단일 vs 멀티: 선택 기준

멀티 에이전트가 항상 더 좋은 것은 아니다. 구조가 복잡해질수록 설계 비용, 디버깅 난이도, API 비용이 모두 올라간다.

<!-- [이미지: 단일 vs 멀티 에이전트 선택 기준 표.
X축: 작업 복잡도 (낮음→높음)
Y축: 역할 분리 필요성 (낮음→높음)
4사분면:
좌하단: "챗봇/단순 워크플로우로 충분"
우하단: "단일 에이전트"
좌상단: "워크플로우 + 단일 에이전트"
우상단: "멀티 에이전트"] -->

![단일 vs 멀티 에이전트 선택 기준](/assets/image/ai-agent-07/selection-guide.png)

```
단일 에이전트가 적합한 경우
  - 처리 단계가 2개 이하
  - 도구가 2개 이하
  - 결과물이 단순한 텍스트

멀티 에이전트가 적합한 경우
  - 처리 단계가 3개 이상이고 각 단계의 품질이 중요
  - 병렬로 처리 가능한 독립적 작업이 있음
  - 중간 결과물을 검증하는 단계가 필요
  - 최종 결과물의 신뢰도가 중요한 업무 (보고서, 분석 자료)
```

## 8. 전체 정리

지금까지 7편에 걸쳐 AI Agent 설계의 핵심 개념을 정리했다. 각 편의 핵심을 한 줄씩 요약한다.

| 편 | 핵심 메세지 |
|---|---|
| 1편: LLM 작동 원리 | AI는 다음에 올 확률이 높은 토큰을 이어붙인다. 정답을 아는 것이 아니다. |
| 2편: 프롬프트 5원칙 | Role·Task·Context·Few-shot·Format. 맥락을 설계하면 결과가 달라진다. |
| 3편: 세 구조 비교 | 판단 주체가 누구인가. 챗봇은 사용자, 워크플로우는 설계자, 에이전트는 AI. |
| 4편: 워크플로우 설계 | Input→Process→Output으로 업무를 분해하면 노드 구조가 보인다. |
| 5편: 에이전트 전략 | ReAct는 투명하고 느리다. Function Calling은 빠르고 간결하다. |
| 6편: RAG | AI가 답하기 전에 문서를 먼저 읽게 만들면 할루시네이션이 줄어든다. |
| 7편: 멀티 에이전트 | 역할을 나누면 품질이 올라간다. 에이전트 하나에 역할 하나. |


이 시리즈를 통해서 전달하고자하는 메시지는 하나다.

> AI 도구를 잘 쓰는 것과 AI 시스템을 설계하는 것은 다르다. 
> 도구 사용법은 도구가 바뀌면 낡아진다. 하지만 설계 사고는 도구가 바뀌어도 남는다.

Dify가 내일 다른 도구로 대체되어도, 여기서 다룬 개념들은 그대로 쓸 수 있다. 
LLM의 확률 기반 생성, 프롬프트의 구조, 워크플로우의 노드 사고, 에이전트의 판단 루프, RAG의 검색-생성 구조, 멀티 에이전트의 역할 분리. 
이것들은 도구가 아니라 AI 시스템 설계의 기본 언어다.
