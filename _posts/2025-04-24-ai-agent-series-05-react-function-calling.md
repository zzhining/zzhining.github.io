"에이전트가 알아서 다 해준다고 했는데, 왜 이상한 답이 나오죠?"

1. 기업 AI 교육 현장에서 에이전트를 처음 써본 수강생들이 가장 많이 하는 말이다. 에이전트는 강력하지만 그만큼 오해도 많다. AI가 스스로 판단한다는 것이 "무조건 잘 한다"는 뜻이 아니다. 어떤 전략으로 판단하게 할 것인지, 그 판단을 얼마나 믿을 수 있는지를 설계자가 이해하고 통제해야 한다.

2. 5편에서는 에이전트의 두 가지 판단 전략인 ReAct와 Function Calling을 비교하고, 실무에서 어떤 기준으로 선택해야 하는지를 정리한다.

---

## 1. 에이전트가 판단한다는 것의 의미

3. 3편에서 다뤘듯이 에이전트는 "목표와 도구를 받고, 어떻게 달성할지 AI가 스스로 판단하는 구조"다. 여기서 핵심은 **판단의 방식**이다. AI가 어떤 방식으로 다음 행동을 결정하는가에 따라 두 가지 전략으로 나뉜다.

<!-- [이미지: 두 전략 비교 개요 다이어그램.
왼쪽: "ReAct" - "생각(Thought) → 행동(Action) → 관찰(Observation)" 루프가 여러 번 반복되는 나선형
오른쪽: "Function Calling" - "입력 → LLM 판단 → 도구 선택 → 실행 → 결과 반환" 단방향 흐름
두 전략 아래에 각각 "투명하고 느림", "빠르고 간결함" 키워드 표시] -->

## 2. ReAct: 생각하고 행동하고 관찰한다

4. ReAct는 Reasoning(추론)과 Acting(행동)의 합성어다. AI가 행동하기 전에 먼저 생각하고, 행동한 결과를 관찰한 뒤 다시 생각하는 루프를 반복한다.

```
Thought   : 상황을 분석하고 다음 행동을 추론
Action    : 결정한 도구를 실제로 호출
Observation: 도구 실행 결과를 확인
→ 다시 Thought로 돌아가 재판단
→ 충분한 정보가 모였다고 판단하면 Final Answer 출력
```

<!-- [이미지: ReAct 루프 상세 다이어그램.
원형 또는 나선형 구조.
"Thought → Action → Observation" 3단계가 반복되는 흐름.
루프 안쪽에 "반복" 표시, 바깥으로 빠져나가는 화살표에 "Final Answer" 표시.
각 단계 옆에 예시 텍스트:
Thought: "2025년 AI 트렌드 최신 정보가 필요하다."
Action: "Tavily.search('2025 AI trends')"
Observation: "검색 결과 5개 반환. 논문도 확인 필요."
→ Thought: "ArXiv에서 논문도 찾아야겠다."] -->

5. ReAct의 가장 큰 특징은 **추론 과정이 텍스트로 출력된다**는 것이다. AI가 왜 그 도구를 선택했는지, 결과를 보고 어떻게 재판단했는지가 Thought 텍스트로 그대로 나온다. 이것이 ReAct의 투명성이다.

**ReAct 실행 예시**

```
사용자 입력: "2025년 생성 AI 에이전트 최신 트렌드를 조사해줘"

Thought: 최신 트렌드를 조사하려면 웹 검색이 필요하다.
         Tavily로 먼저 검색한다.

Action: Tavily.search("2025 AI agent trends")

Observation: 검색 결과 5개 반환됨.
             OpenAI, Anthropic, Google의 에이전트 발표 내용 포함.
             학술적 근거도 필요할 것 같다.

Thought: 논문도 함께 확인하면 더 신뢰도 있는 답변이 가능하다.

Action: ArXiv.search("multi-agent systems 2025")

Observation: 논문 3편 확인됨.
             충분한 정보가 수집되었다.

Final Answer: 수집된 정보를 종합해서 리포트를 작성한다.
```

6. ReAct는 오픈 모델을 포함한 대부분의 LLM과 호환된다. 모델 자체의 특수 기능에 의존하지 않고 텍스트 생성 능력만으로 작동하기 때문이다.

---

## 3. Function Calling: 모델이 직접 도구를 선택한다

7. Function Calling은 OpenAI가 표준화한 방식으로, LLM 모델 자체에 "어떤 도구를 호출할지 결정하는 기능"이 내장된 전략이다. 추론 과정을 텍스트로 출력하지 않고, 모델이 내부적으로 판단해서 도구를 바로 호출한다.

<!-- [이미지: Function Calling 흐름 다이어그램.
"사용자 입력 → LLM(내부 판단) → 도구 선택 및 파라미터 생성 → 도구 실행 → 결과 반환 → LLM(최종 답변 생성)"
단방향 직선 흐름. "내부 판단" 박스에 "추론 과정 비공개" 주석 표시] -->

8. Function Calling의 작동 방식을 단순화하면 이렇다.

```
입력: "오늘 서울 날씨 알려줘"

LLM 내부 판단: weather_api를 호출해야 함
               파라미터: {"location": "서울", "date": "today"}

도구 실행: weather_api(location="서울", date="today")

결과 반환: {"temp": 18, "condition": "맑음"}

최종 답변: "오늘 서울은 18도이며 맑습니다."
```

9. 추론 과정이 외부로 나오지 않기 때문에 응답이 빠르다. 불필요한 Thought 텍스트를 생성하지 않으므로 토큰 소모도 적다. 단, GPT-4o, Claude 3.5 등 Function Calling을 지원하는 모델에서만 작동한다.

## 4. 두 전략 비교

10. 두 전략의 차이를 실무 관점에서 비교하면 이렇다.

| 항목 | ReAct | Function Calling |
|---|---|---|
| 추론 방식 | Thought→Action→Observation 루프 | 모델 내부 기능으로 직접 판단 |
| 속도 | 느림 (루프 반복) | 빠름 |
| 투명성 | 높음 (추론 과정 텍스트 출력) | 낮음 (내부 판단 비공개) |
| 토큰 비용 | 높음 | 낮음 |
| 오픈 모델 호환 | 대부분 가능 | 제한적 |
| 추천 상황 | 리서치, 교육용 시연, 복잡한 멀티스텝 | 정형 업무, 실서비스 배포 |

<!-- [이미지: 두 전략 선택 가이드 다이어그램.
"투명성이 중요한가?" → Y: ReAct
"오픈 모델을 쓰는가?" → Y: ReAct
"속도와 비용이 중요한가?" → Y: Function Calling
"실서비스로 배포하는가?" → Y: Function Calling
의사결정 트리 형태] -->

## 5. 에이전트 사용 시 반드시 통제해야 할 것들

11. 에이전트는 강력하지만 통제하지 않으면 예상치 못한 결과가 나온다. 기업 실무에 도입할 때 반드시 설정해야 할 항목 네 가지를 정리한다.

**① Max Iterations (최대 반복 횟수)**

에이전트는 목표를 달성할 때까지 루프를 반복한다. 반복 횟수에 제한을 두지 않으면 API 비용이 무한정 늘어날 수 있다. 일반 업무에는 5~10회가 적당하다.

```
Max Iterations: 7  ← 이 이상 반복하면 강제 종료
```

**② Instructions의 명확성**

에이전트에게 주는 지시(Instructions)가 모호하면 엉뚱한 도구를 선택한다. 2편의 프롬프트 5원칙을 그대로 적용한다. Role, Task, 행동 순서, 출력 형식을 명확하게 정의해야 한다.

```
# 모호한 Instructions (나쁜 예)
"정보를 찾아서 알려줘"

# 명확한 Instructions (좋은 예)
# Role
당신은 전문 리서치 에이전트입니다.

# Task
사용자 질문에 답하기 위해 아래 순서로 행동하세요.
1. Tavily로 최신 웹 정보를 검색합니다. (2~3회)
2. 관련 논문이 있다면 ArXiv에서 추가 검색합니다. (1회)
3. 수집한 정보를 종합해 아래 형식으로 답변합니다.

# Format
## 핵심 요약 (3줄 이내)
## 상세 내용
## 출처
```

**③ Hallucination 검증**

에이전트는 도구 결과를 무시하고 학습 데이터 기반으로 답할 수 있다. 중요한 업무라면 에이전트 뒤에 검증 노드를 추가하거나, Instructions에 "반드시 도구 결과만 사용할 것"을 명시한다.

**④ 도구 수 제한**

도구가 많을수록 에이전트의 선택 오류 가능성이 높아진다. 필요한 도구만 선별해서 연결한다. 리서치 에이전트라면 Tavily + ArXiv 두 개로도 충분하다.

## 6. 에이전트 vs 워크플로우: 언제 무엇을 선택하는가

12. 에이전트를 쓴다고 항상 결과가 좋은 것은 아니다. 기업 교육 현장에서 가장 많이 보는 실수가 "모든 것을 에이전트로 만들려는 것"이다. 단계가 고정된 업무에 에이전트를 쓰면 비용만 높아지고 결과는 오히려 불안정해진다.

<!-- [이미지: 에이전트 vs 워크플로우 선택 매트릭스.
X축: 업무 복잡도 (낮음 → 높음)
Y축: 단계 가변성 (고정 → 유동)
4개 사분면:
좌하단: "챗봇" (복잡도 낮음, 단계 고정)
우하단: "워크플로우" (복잡도 높음, 단계 고정)
좌상단: "불필요한 에이전트" (복잡도 낮음, 단계 유동) → 워크플로우로 대체 권장
우상단: "에이전트" (복잡도 높음, 단계 유동)] -->

13. 판단 기준을 한 문장으로 정리한다.

> 처리 단계가 고정되어 있다면 워크플로우, 상황에 따라 다른 도구와 순서가 필요하다면 에이전트.

**에이전트가 적합한 업무**
- 최신 정보를 검색하고 종합해야 하는 리서치
- 사용자 질문의 의도가 다양하고 예측하기 어려운 상담
- 여러 외부 API를 상황에 맞게 조합해야 하는 처리

**워크플로우가 더 나은 업무**
- 매주 같은 형식의 보고서 생성
- 이메일 분류 및 표준 답변 초안
- 특정 양식의 문서 자동 생성

## 7. Dify에서 에이전트 설정하는 법

14. Dify에서 에이전트 앱을 만들 때 설정해야 할 항목을 순서대로 정리한다.

<!-- [이미지: Dify 에이전트 설정 화면 구조 다이어그램.
전체 설정 화면을 영역별로 표시:
상단: "모델 선택 (gpt-4o-mini 권장)"
중간 상단: "전략 선택 (ReAct / Function Calling)"
중간: "Max Iterations 설정 (권장: 7)"
중간 하단: "Tools 추가 (Tavily, ArXiv 등)"
하단: "Instructions 입력창"
각 영역을 박스로 구분하고 순서 번호 표시] -->

```
1. Studio → Create App → Agent → 이름 입력
2. 모델: gpt-4o-mini
3. 전략: ReAct (투명성 확인용) 또는 Function Calling (실서비스)
4. Max Iterations: 7
5. Tools: Tavily Search + ArXiv
6. Instructions: Role + 행동 순서 + Format 정의
7. 우측 채팅창에서 테스트 → Publish
```

15. ReAct 전략을 선택하면 채팅창에서 Thought → Action → Observation 과정이 실시간으로 표시된다. 처음 에이전트를 만들 때는 ReAct로 시작해서 판단 흐름을 확인한 뒤, 안정화되면 Function Calling으로 전환하는 것이 실용적인 순서다.

## 8. 정리

16. 에이전트의 판단 전략은 두 가지다.

- **ReAct**: 생각하고 행동하고 관찰하는 루프. 투명하지만 느리다. 복잡한 리서치, 교육용 시연에 적합하다.
- **Function Calling**: 모델이 내부적으로 판단해서 바로 도구를 호출한다. 빠르지만 추론 과정이 보이지 않는다. 정형화된 실서비스에 적합하다.

17. 전략을 선택하는 것만큼 중요한 것이 통제다. Max Iterations 설정, Instructions의 명확성, 도구 수 제한, Hallucination 검증. 이 네 가지가 갖춰진 에이전트가 실무에서 쓸 수 있는 에이전트다. 강력한 도구일수록 통제 설계가 먼저다.
